## 一、架构演进路线总览

```
Phase 1: CLI 工具集          Phase 2: MCP 封装           Phase 3: 全平台
┌─────────────────┐    ┌─────────────────┐    ┌─────────────────────┐
│ quality-check   │    │ MCP Server      │    │ Web 管理后台        │
│ content-gen     │    │ (stdio for 个人) │    │ 多人协作平台        │
│ knowledge-build │──► │ (SSE for 团队)  │──► │ SaaS 服务           │
│ issue-resolve   │    │                 │    │ API 网关            │
│ maintenance-scan│    │                 │    │                     │
└─────────────────┘    └─────────────────┘    └─────────────────────┘
    零依赖，本地运行       Agent 可调用           团队级协作平台
    人人可用               CLI 能力不变           CLI+MCP 仍可用
```

**核心原则：每阶段完全向下兼容，前阶段能力不因升级而失效。**

## 二、Phase 1: CLI 工具集 (当前阶段)

### 2.1 设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 交付形态 | CLI（命令行工具） | 零学习成本，人可用，脚本可用，CI/CD可用 |
| 核心语言 | Python 3.11+ | AI Agent生态最好，跨平台，不需要编译环境 |
| 包管理 | pip + pyproject.toml | 标准做法，`pip install -e .` 即可使用 |
| 规则引擎 | Vale 本地二进制 | 文档Lint行业标准，规则可定制，离线运行 |
| 模板引擎 | Jinja2 | Python生态，功能完备 |
| 配置文件 | YAML + JSON Schema | AI易读易写，支持校验 |
| 文档解析 | markdown-it-py | Python最好的MD解析器 |

### 2.2 优缺点

| 维度 | 评价 |
|------|------|
| 上手成本 | ★★★★★ 极低。`pip install` 就能用，命令和 git 一样直观 |
| 部署成本 | ★★★★★ 零。不需要服务器，不需要网络 |
| AI支持 | ★★★☆☆ Agent 可通过 CLI 调用，但不原生 |
| 多人协作 | ★★★☆☆ 共享知识库通过 Git 同步 |
| 可扩展性 | ★★★★☆ 加新命令 = 加一个 Python 文件 |

### 2.3 适合场景

- 个人开发者使用
- CI/CD 流水线集成
- 小团队（<10人）通过 Git 共享知识库
- 内网/离线环境

## 三、Phase 2: MCP 封装 (下阶段)

### 3.1 设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 封装方式 | stdio MCP Server | 零网络依赖，CLI 已有能力，MCP 只是加一层协议 |
| 协议实现 | 基于 mcp Python SDK | 官方维护，成熟稳定 |
| 多人模式 | 可选 SSE 模式 | 需要时再开服务器，不强制 |
| 工具粒度 | 与 CLI 命令一一映射 | 保持一致，降低理解成本 |

### 3.2 MCP vs CLI 对比

| 对比项 | CLI | MCP (stdio) | MCP (SSE) |
|--------|-----|-------------|-----------|
| 安装方式 | pip install | pip install + Agent配置 | 同左 |
| 网络依赖 | 无 | 无 | 需要内网HTTP |
| AI 调用 | 自然语言+shell | Agent原生调用 | Agent原生调用 |
| 人用 | ✅ 直接终端用 | ❌ 必须通过Agent | ❌ |
| 脚本调用 | ✅ | ❌ | ❌ |
| 多人共享 | Git同步知识库 | 同左 | 中心化Server |
| 维护成本 | 低 | 中（需维护MCP适配） | 中高（需维护服务器） |

### 3.3 Phase 2 前提条件

在进入 Phase 2 之前，需确认：
1. [ ] CLI 工具已稳定运行，核心功能经过验证
2. [ ] 有明确的 Agent 集成需求（用户要求了再用）
3. [ ] CLI 覆盖了所有核心场景，MCP 只是协议封装而非功能补充

### 3.4 优缺点

| 维度 | 评价 |
|------|------|
| 上手成本 | ★★★★☆ 配一次 config 即可，但对不懂 MCP 的用户有门槛 |
| AI支持 | ★★★★★ Agent 原生发现和调用工具 |
| 离线支持 | ★★★★★ stdio 模式完全离线 |
| 维护成本 | ★★★☆☆ 多一层 MCP 适配需要维护 |
| 成熟度 | ★★★★☆ MCP 协议已稳定，但生态仍在发展中 |

## 五、关键技术决策记录

### ADR-001: 为什么第一阶段选 CLI 而不是 MCP？

| 项目 | 内容 |
|------|------|
| 日期 | 2026-06-02 |
| 状态 | 已采纳 |
| 选项 | CLI vs MCP vs 直接Python库 |
| 决策 | CLI 优先 |

**理由：**
1. CLI 是人、脚本、CI/CD 都能用的最低成本方案
2. MCP 依赖 Agent 生态成熟度，过早引入增加复杂度
3. CLI 做好了，MCP 只是加一层协议适配（`mcp_server.py` 调用已有工具函数）
4. 如果用户不需要 Agent 集成，CLI 就已经解决了核心问题

**风险：**
- 后续 MCP 封装可能需要重构 CLI 参数结构
- 缓解：工具函数与 CLI 入口分离，CLI 只是薄薄一层

### ADR-002: 为什么选 Python 而不是 Go/TypeScript？

| 项目 | 内容 |
|------|------|
| 日期 | 2026-06-02 |
| 状态 | 已采纳 |
| 选项 | Python vs Go vs TypeScript |
| 决策 | Python |

**理由：**
1. AI Agent 生态最好（LangChain、MCP SDK、各类解析器）
2. Vale 生态本身是 Go，但封装调用不需要 Go
3. 文档处理生态（markdown-it-py、openpyxl、tree-sitter）Python 最成熟
4. 团队（或 AI Agent）开发和调试 Python 效率最高

**风险：**
- Python 分发需要运行时环境
- 缓解：可以用 PyInstaller 打包成单 exe 作为最终分发形态

### ADR-003: 知识库构建是核心能力

| 项目 | 内容 |
|------|------|
| 日期 | 2026-06-02 |
| 状态 | 已采纳 |
| 决策 | 将知识库构建器（Knowledge Builder）提升为产品核心 |

**理由：**
1. 这是方案最独特的价值——市面上没有成熟的"从客户文档自动提取规则"的方案
2. 知识库质量直接决定后续所有 Skill 的效果
3. 知识库是可积累的资产——客户投入越多，方案越精准

### ADR-004: 规则采用两级分类

| 项目 | 内容 |
|------|------|
| 日期 | 2026-06-02 |
| 状态 | 已采纳 |
| 决策 | 确定性规则（Vale/规则引擎执行）+ 模糊性规则（AI+人工确认） |

**理由：**
1. 确定性规则：快、准、可复现，适合格式/结构/风格检查
2. 模糊性规则：需要理解上下文，适合描述清晰性/完整性判断
3. 两者互补，而非替代

## 六、已知风险

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|----------|
| Vale 文档Lint规则编写成本高 | 知识库构建难度 | 中 | 先提供预置规则模板；知识库构建器自动生成基础规则 |
| 不同客户差异过大 | 产品通用性不足 | 高 | 知识库构建器作为核心能力，专注于适配不同输入 |
| MCP 协议生态变化 | Phase 2 需调整 | 低 | CLI 能力独立于 MCP，协议变化只需改 MCP 适配层 |
| AI Agent 对工具的使用不可控 | 预期之外的行为 | 中 | 工具设计时考虑边界保护，参数强校验 |
