# 产品PRD文档

资料开发、测试、维护、问题解决——全链路解决方案


## 背景：

我要给不同的公司提供上述解决方案，可能是大公司例如华为、苹果、谷歌、淘天、腾讯等等。他们可能是例如华为的HarmonyOS开发团队，他们有开放给开发者接入的接口（ArkTS API、也有云侧的REST API），ios、android也是类似的，都存在操作系统直接开放的接口。或者类似微信、支付宝业务，提供有获取相关账号信息等类似接口，均需要维护开发者资料，此产品即提供全流程解决方案，为资料开发、测试、维护、问题解决提供AI Agent解决方案，节省人力，由AI结合此解决方案主导开发，人力审核，已达到提升效率、解放人力的诉求

## 要求

1. 解决方案中不要考虑并涉及opus、gpt等LLM大模型或如claude code等AI Agent内容。此产品允许客户使用任何LLM、Agent产品接入，因为这就只是一套解决方案，可能是skill集合，也可能是workflow工作流，形式暂未确定
2. 要求尽量全部使用本地功能，不依赖网络
3. 因为不同的客户、公司可能文档、资料的内容、风格完全不一致，并且其部分资料开发源文档都是不对外的，因此本产品需具备由客户的资料源文档、测试标准、格式检查等等信息，总结梳理出可用于解决方案的知识库或检查项的能力，这个方式我也不太确定，可以再完善下，结合业界先进方案完善下
4. 刚刚这一条我再解释下，因为产品定义不是全流程嘛，所以我期望就是：
  
    1. 客户提供必要的输入，可能是：源文档（以华为公司HarmonyOS相关业务部门为例，后续也都以这个为例：可能是其开放的API参考文档、应用开发指南文档、元服务开发指南文档等）、开放的SDK接口声明文件、sampleCode、codelab工程等，这些文档啊工程啊，可能各自都具备一些独有的风格和格式要求。除了现有的源文档之外，可能还有一些文档的测试标准或规格要求（例如要求资料的术语使用、内容一致性、示例代码可用、文档风格符合HarmonyOS鸿蒙风格、要求API接口必须包含某些必要信息、指南文档必须满足某些格式等等，形式上可能是xlsx表格，里面列举了所有的测试用例或测试标准等等）。此解决方案可根据用户的输入（即上述内容等等），来构建必要的知识库或必要的解决方案架构
    2. 有了上述架构或前提后，已构建一个初版的完整解决方案。之后我依次讲解开发、测试、维护、问题解决等流程中的期望效果：
    3. 开发：开发阶段，用户可能会有一些输入，比如是要在API参考、应用指南资料中新增某个章节或某些内容，解决方案会向用户索取必要的输入，进而根据已有的文档风格、模板进行开发，生成对应的新内容，此内容要满足用户的测试标准，能通过测试检查。之后由用户进行人工审核，并能根据用户意愿进行调整，但是必须满足风格、规格、模板、测试标准等等
    4. 测试：解决方案可构建必要的资料或sample（ArkTS）工程的可维护手段，根据用户输入构建的测试标准等，能根据用户需要，定时或随时进行测试，以发现是否存在历史问题或新问题。该能力可能是个原子化功能，独立开来，能放在开发阶段的同时进行测试，以满足用户提供的风格、规格、模板、测试标准，也可以在其他所有的阶段中结合测试
    5. 维护：其实和测试相关，就是可以不同时间段或不同周期，检查已有内容是否满足规格，因为可能客户团队的内容没有变更，但是其相关领域内容变更导致客户的资料或sample工程新增问题，也要能及时检查维护，及早解决
    6. 问题解决：客户团队的测试团队，也可能会在不同版本对资料、sample工程进行测试，可能会产生一些问题。解决方案要能根据测试提出的问题单进行定向解决。测试提出的可能不是问题，那则要有对应的规格或证据证明为非问题，哦因此此解决方案必须构建客户团队的相关知识库，用于实践总结等。如果是问题，则需要解决方案最小化解决测试问题，同时满足风格、规格、模板、测试标准等要求。解决完成后，由客户进行人工审核。
    7. 可扩展性：解决方案必须有自进化的方式，因为客户提供的风格、规格、模板、测试标准可能会有变更或者新增，需要能根据输入，对解决方案整体进行适配修改。

5. 要求必须是AI友好的，因为说了用户可能使用不同类型的AI Agent接入此解决方案，能更高效的解决其开发、测试、维护、解决问题的诉求。上述提到的此解决方案工程的可维护性（支持修改、新增此解决方案项目自身等），也可以构建AI友好的，支持通过skill、workflow等方式来维护项目本身。
6. 要是AI好维护的，比如要构建项目架构文档、readme、要写短期长期的项目开发迭代计划、保存项目开发进度和下一步计划的文档（相当于历史记录或上下文，能在每次agent任务中断后也能顺利继续项目的开发迭代等）
