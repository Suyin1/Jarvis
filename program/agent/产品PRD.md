理解你的约束：**只能使用公司内部的单一Agent（或有限LLM），不能依赖外部的多Agent平台**，但可以用多个进程并发执行。目标是建立一套**不受特定Agent和LLM限制的、可复现的开发与维护模式**，来生成和维护ArkTS+QT的示例工程。

这实际上是把问题从“选什么框架”转向“设计一套工作流与方法论”。核心思路是：**将工程生成过程工业化，变成一条可被任何Agent（甚至人）按步骤执行的标准流水线**，而你只作为输入者和决策者。

以下是一套完整的、不绑定技术的模式设计。

---

## 一、核心模式：基于契约的“规划-生成-集成-验证”循环

这套模式借鉴了编译器前端（词法分析→语法分析→代码生成）和持续集成思想，**将开发过程解耦为四个标准化的独立阶段**，每个阶段都可以由独立的Agent进程（或人）完成，互不干扰。

### 整体架构图（抽象）
```
人类输入需求
     ↓
[阶段0：知识库 & 模板] （预置，人工维护一次）
     ↓
[阶段1：规约生成]     → 输出《功能规约》+《接口契约》
     ↓
[阶段2：并行代码生成]  → 多个Worker进程，每个生成独立模块代码
     ↓
[阶段3：集成与构建]   → 执行编译、链接、打包脚本
     ↓
[阶段4：自动化验证]   → 运行测试，收集失败信息
     ↓          ←───────────────── 失败则自动生成修复任务，回阶段2
   （通过）→ 产物归档 + 记忆更新
```

**关键原则**：
- **所有中间产物都是可阅读的文本文件**（Markdown规约、头文件、CMake、代码文件、构建日志、测试报告），不依赖黑盒状态。
- **每个阶段只依赖前阶段的标准化输出，不共享Agent上下文**。
- **任何Agent（或人）只需阅读上一阶段的产物，就能接手工作**。这使你可以随时替换LLM，甚至人工顶替某个环节。

---

## 二、阶段详解与实施细节

### 阶段0：知识库与模板（一次性建设）
你需要从预研工程（不可用的那个）中提炼出**可复用的知识**，形成两个文件化资产：
1. **QT与ArkTS桥接开发手册**（文本，约5-10页）：包含NAPI注册模式、线程模型、序列化方式、CMake配置要点、鸿蒙工程配置要点、常见错误模式及解决。
2. **最小可运行示例模板**（代码+注释）：一个极简的“QT点击→NAPI→ArkTS显示Hello”工程，结构清晰，可作为后续所有生成的“黄金参考”。

**作用**：任何Agent在生成前，必须先读取这些知识库（通过检索或直接作为system prompt的静态内容）。这保证了“预研思路”的传承。

### 阶段1：规约生成（一个Agent，或人+Agent）
你输入自然语言需求，例如：“新增一个示例：QT侧输入文本，通过NAPI处理后返回给ArkTS显示为Toast，并记录日志”。

Agent（或你自己）需要输出一份**结构化规约文档**，包含：
- **功能描述**：交互流程、状态变化。
- **接口契约**：
  - C++头文件声明（QT侧暴露给NAPI的类和方法）。
  - NAPI桥接层的函数签名。
  - ArkTS侧导入的模块和方法声明。
- **文件清单**：需要新建或修改哪些文件，路径如何。
- **构建配置变更**：CMakeLists需要添加哪些源文件、链接库；鸿蒙oh-package.json5需要哪些依赖。
- **验收测试用例**：至少3个明确的可执行验证步骤，如“运行应用→点击按钮→看到Toast文字为‘处理完成’”。

**此步骤的价值**：将模糊需求固化为可审计、可分发的“合同”，后续阶段完全据此执行，不用回溯原始需求。

### 阶段2：并行代码生成（多进程Worker）
这是你利用“多进程”的关键环节。**启动多个Agent进程，每个只负责一个独立模块的代码生成**，互不依赖（只共享阶段1的规约）。

典型分工：
- **Worker A（QT C++逻辑）**：根据契约生成C++实现、修改CMakeLists。
- **Worker B（NAPI胶水层）**：生成NAPI的C++包装代码（如果复杂，可单独拆）。
- **Worker C（ArkTS UI）**：生成ArkTS页面代码、导入声明。
- **Worker D（鸿蒙配置）**：更新oh-package.json5、build-profile等。

**执行要求**：
- 每个Worker接收相同的输入：规约文档 + 知识库 + 当前完整代码库的快照。
- Worker只输出自己负责的文件（完整内容或diff），不允许修改其他模块文件。
- 输出写入约定的临时目录，比如 `output/cpp/`、`output/ets/`，避免冲突。

**优势**：即使公司只有一个万能Agent，你也可以同时开4-5个进程，每个赋予不同的系统提示和专长描述，大幅提速。单个进程失败不会整体崩溃，未通过的模块可单独重试。

### 阶段3：集成与构建（脚本化，无需Agent思考）
本阶段**不建议用Agent**，直接用确定性脚本执行。这能避免LLM幻觉导致的不稳定。

脚本流程：
1. 将阶段2输出的代码文件合并到工作区对应路径。
2. 执行QT侧编译（`cmake --build`），收集编译错误日志。
3. 执行鸿蒙侧编译（`hvigorw assemble`），收集错误。
4. 如果任一编译失败，**将错误日志按模块分类，生成“修复任务描述”**，例如：
   - “文件 `bridge.cpp:32` 使用了未声明的函数 `CallArkTS`，请检查头文件包含和NAPI注册。”
   - 修复任务被打回阶段2，只分发给对应模块的Worker。
5. 编译通过后，进行链接和打包，产生可运行的应用包。

这个闭环最多迭代3-5次，通常即可收敛。脚本与Agent完全解耦。

### 阶段4：自动化验证与自愈
- 运行测试用例（可以是自动化的UI测试，或嵌入在应用内的自检脚本），输出测试报告。
- 测试Agent（可复用阶段2的Worker）读取失败信息，尝试生成修复补丁。
- 修复同样按模块归因：如果是QT逻辑错误，交Worker A；如果是ArkTS显示错误，交Worker C。
- 循环“修复→构建→测试”，直到全部通过，或超过次数后暂停请求人工介入（此时你只需看一眼错误摘要，给出方向性指令）。

### 记忆与进化
- 每完成一个示例，将**规约+最终代码+修复过程中的关键教训**整理成一篇文档，存入知识库。
- 未来类似需求，Agent可检索此文档作为few-shot，大幅降低生成难度。

## 三、不依赖多Agent框架的并行协作机制

你只需一个“单一Agent”的API，但可以通过如下方式实现并行：

- **消息队列模式**：使用简单的任务列表（如文本文件、Redis、甚至Git issue）。主控进程写入N个子任务描述，然后启动N个Agent进程，每个从队列取一个任务处理，输出到约定目录。主控监控输出完整性。
- **分而治之的提示词工程**：为不同Worker设置不同的system prompt（如“你是QT/C++专家”“你是ArkTS UI专家”），共用同一个LLM endpoint。
- **状态共享完全通过文件系统**：代码库使用Git管理，每个Worker在分支上工作，主控负责合并。冲突由规则处理（不同模块不同文件，通常无冲突）。

这实际上就是一种**本地化、简化版的MetaGPT SOP**，但不需要任何额外框架，纯靠脚本调度。

## 四、业界先进方案的模式借鉴（抽象层面）

虽然你不能使用那些平台，但它们的核心思想可以移植：

| 方案 | 可借鉴的模式点 |
|------|---------------|
| **Devin** | “计划-执行-验证”闭环；每一步操作可被中断和回滚。 |
| **MetaGPT** | 将开发流程抽象为标准操作流程（SOP），用文档作为Agent间通信媒介。 |
| **SWE-agent** | 为Agent设计受限但高效的操作空间（文件编辑、shell命令），避免动作空间爆炸。 |
| **RAG模式** | 所有生成都必须检索相关知识，保证一致性。 |
| **AutoCodeRover** | 基于错误日志和代码结构做修复，而非反复试错。 |

你的模式将融合这些点：**SOP化流程 + 文档契约 + 约束的工具使用 + RAG + 结构化修复**。

## 五、你作为人的最小参与接口

你的工作将精简到以下几步：
1. **需求输入**：一句话或一段描述。
2. **规约审核**（可选）：Agent生成的规约草案可以自动执行，但若你希望风格统一或架构正确，可以花几分钟审核并回复“同意”或“修改接口X”。
3. **卡点裁决**：当自动修复超过3次失败，系统暂停，你查看简要摘要，给出一个提示，如“NAPI序列化应使用rawdata模式”。
4. **知识库维护**（初期）：将预研成果抽象为手册，这个一旦建立，极少修改。

整个过程就像你给一个高度自律的外包团队分配任务，你只需输入需求、偶尔指点方向。

## 六、起步实操建议（不受限于Agent的具体启动方式）

**第一步：人工手动走通一遍流水线**
- 选一个简单的示例，自己充当每个阶段，产出规约→各模块代码→构建→测试，并整理出每一步的**精确命令和预期输出**。
- 将预研思路写入知识库文档，将最小示例工程做成模板。

**第二步：用脚本固化“集成与构建”和“错误归因”**
- 编写确定性的构建脚本和错误分类脚本（可用正则匹配常见错误模式），让这步零LLM依赖。

**第三步：编写Agent提示词模板，分别对应各Worker**
- 制作几套精炼的system prompt，加载了知识库和模板工程的部分内容。
- 用阶段1的一个Agent实例生成规约，然后调用多个Worker并发生成代码。

**第四步：串联成流水线，加入自动修复循环**
- 用一个主调度脚本（shell/Python）控制整个流程：调用Agent→合并代码→构建→测试→修复回环。
- 初期你可以手动触发，最终做到定时或事件驱动。

这套模式完全不受限于你未来LLM的升级或更换，因为每个环节的输入输出都是标准文本，任何符合接口的模型都能嵌入。你构建的是一套**开发工程化系统**，而不仅仅是“用AI写代码”。

---

通过这种“契约驱动、分治并行、脚本固化、闭环自愈”的模式，你就能在公司内网用单一Agent建立一套自动化的sample工程开发维护体系，人力参与降到极低，且具备长期演进能力。
